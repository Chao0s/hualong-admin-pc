# Admin ADR-0001 · 成长册设置独立为顶层视图，以及管理端的模块边界判准

> **状态**：已接受 · 2026-08-03
> **范围**：只影响管理端控制台。跨端的成长册归属规则不在本文，见 `hualong-backend/docs/ADR-0012`
> **相关**：[`../../decision.md`](../../decision.md) 第 1 条 · `hualong-backend/DECISIONS.md` E9 · `db/GAPS.md` G32

---

## 1. 背景

管理端原有 8 个视图，分三组（总览 / 课程与教研 / 园务管理）。新功能来了要决定挂在哪——这个问题在成长册设置这次暴露出来，而且**必然还会再来**。

这次的具体经过：园所要配置成长册的公共内容（封面、园所介绍、园长寄语等），起初判断为「组织管理加一个 Tab」——当时范围只有两个字段（`db_school.book_cover` 与 `school_intro`），Tab 装得下，且 `db_school` 本来就是园所主数据的根，与教师/班级/幼儿同层。

随后范围扩大：加上 logo、模板选择、按年级的园长寄语、园所栏目、整册预览、草稿/发布状态机——变成「一园一套的册子配置 + 分发给教师端」。Tab 不再合适。

**问题不在于这次选错了，在于当时没有可复用的判准**，每次都要从头论证一遍。

## 2. 决策

### 2.1 成长册设置独立为第九个顶层视图

`index.html#growthbook`，放在「园务管理」组，位于内容发布之后。配套新增第九份 backend spec `growth-book-setting-spec.md`。

### 2.2 模块边界判准（本决策的主要产出）

新功能该新开顶层视图，还是并入已有模块？依序问三个问题：

**判准一 · 这个对象是列表，还是单例？**

管理端已有模块大多是**列表型**：一批同类记录 + 筛选 + 行内操作。内容发布的完整模型是「列表 + 发布弹层 + 浏览量/下载量 + 下线」，组织管理是「列表 + 新增表单 + 行内编辑」。

**单例配置**（一园一份、没有列表、没有条目生命周期）不属于任何列表型模块。成长册设置就是单例：一套模板、一份园所介绍、一份寄语。硬塞进内容发布会污染那份 spec 的 `CATEGORY_OBJECT_MAP`，而它明写 `generic_content_table = FORBIDDEN`——每个栏目写自己的 canonical 内容表，而 `db_school` 不是内容表。

**判准二 · 它有没有独立的发布/生效语意？**

内容发布的「发布/下线」是资讯的上下架，作用于单条内容。成长册设置的 `d1=draft / d2=published` 是**对教师端的分发闸门**——未发布时全园教师取不到模板、`can_generate=0`。两者名字像，语意不同层。

有独立状态机 → 倾向独立视图，否则用户会把两种「发布」当成一回事。

**判准三 · 新开顶层视图的成本能不能承受？**

成本是明确可算的，因为本仓库采用**冗余记账**：每份 backend spec 的 `[STATIC_BUTTON_NODE_INDEX]` 都完整抄一遍全部导航按钮（这样后端只读一份 spec 就知道该页所有可点节点）。所以加第 N 个视图要动：

- 现有 N−1 份 spec 的导航表各加一行、行号顺延重编、`static_node_count` 与 `runtime_clickable_node_count` 各 +1
- `dashboard-spec.md` 额外两处：`[NAV_OBJECTS]` 表加行、`[JUMP_VALIDATION]` 的视图枚举加值（**这条有行为后果，漏了新页面会被 400 挡掉**）
- `index.html` 的导航项 / `<section>` / `VIEW_META`
- `docs/信息架构.md` 第一节导航图 + 新增一节
- `README.md` 功能概览表
- `hualong-backend/db/spec/screens.tsv` 加一行

**这个成本是真实的，但它不构成把功能塞进错误模块的理由。** 归错模块的代价是长期的（心智模型混乱、spec 污染、后续每个人都要重新理解），加一个视图的代价是一次性的机械劳动。

## 3. 代价

**接受的：**

- 导航从 8 项变 9 项，「园务管理」组现在有 4 项。侧栏仍在一屏内，未触及需要折叠或二级导航的密度。
- **加视图的成本随现有 spec 数线性增长**——这次改 8 份，下一个要改 9 份。冗余记账是刻意的设计（后端读单份 spec 即可获得完整上下文），这是它的账单。若视图数继续增长到需要频繁新增，应重新评估是否把导航抽成单一来源、其余 spec 引用而非抄写。
- 判准一与判准二会把「单例配置」持续推向独立视图。若未来出现第二、第三个单例配置（如园所基础信息、学期设置），不应各开一个视图，而应届时合并为一个「园所设置」模块——**那时本 ADR 需要修订**。

**得到的：**

- 内容发布的 spec 未被污染，`generic_content_table = FORBIDDEN` 这条约束保持有效。
- 成长册设置的发布状态机独立，与资讯上下架不会被混为一谈。
- 下次遇到同类问题有三个可直接套用的问题，不必重新论证。

## 4. 考虑过但否决的方案

| 方案 | 否决理由 |
|---|---|
| **A. 内容发布加一个 Tab** | 模型完全对不上：那是列表型模块（列表 + 发布弹层 + 浏览量 + 下线），成长册设置是单例配置；`FORM_FIELD_INDEX` 的「标题/栏目/正文/附件」四个字段一个都用不上；且该 spec 明写 `generic_content_table = FORBIDDEN`，而 `db_school` 不是内容表 |
| **B. 组织管理加一个 Tab** | **范围只有 2 个字段时这是对的**，`db_school` 与教师/班级/幼儿同为园所主数据。扩到「模板选择 + 素材 + 按年级寄语 + 园所栏目 + 整册预览 + 发布状态机」之后，Tab 的形态装不下，且会让组织管理从「主数据 CRUD」变成混合模块 |
| **C. 挂在家园共育数据下** | 那是纯只读的统计面（四项完成率 + 分班明细），没有任何写入控件。加一个带发布状态机的配置面进去，会破坏它「只读看板」的单一定位 |
| **D. 先不做，等后端 DDL 落地** | G32 已登记为 BLOCKER 且四层全缺（backend spec / `ui=` 标注 / 页面 / `screens.tsv`）。等 DDL 不会让任何一层自己出现——**这四层本来就是 DDL 的输入而不是产物** |

## 5. 后续

本 ADR 在以下情况需要修订：

1. **出现第二个单例配置模块**（园所基础信息、学期设置等）——届时应合并为「园所设置」而非各开视图，判准一需补充「同类单例应聚合」。
2. **视图数继续增长到导航需要分层**——判准三的成本计算方式随之改变。
3. **冗余记账制度被取消**（导航抽成单一来源）——判准三的成本大幅下降，天平右移。
